## 2. КРИТИЧЕСКИЕ ЗАДАЧИ (Critical Tasks — must fix now)

### 🔴 КРИТИЧНО-1: Cron schedule — 1h-напоминания не работают

**Проблема:** `vercel.json` содержит `"0 8 * * *"` — запуск раз в день в 8:00 UTC. Функция `/api/cron/reminders` ищет записи в окне ±30 минут от текущего времени. При запуске раз в день 1h-напоминания работают только для записей в 8:45-9:15 UTC (11:45-12:15 МСК). Все остальные 1h-напоминания **никогда не отправляются**.

**Impact:** Клиенты не получают напоминание за 1 час. Это ключевая фича, которую продаём.

**Решение:**
```json
// vercel.json
{
  "crons": [
    {
      "path": "/api/cron/reminders",
      "schedule": "0 * * * *"
    }
  ]
}
```
Запуск каждый час. Vercel Hobby поддерживает это.

**Effort: S (5 минут)**

### 🔴 КРИТИЧНО-2: Race condition в счётчике сообщений

**Проблема:** `src/lib/telegram/bot-factory.ts:479`:
```typescript
.update({ messages_used: subscription.messages_used + 1 })
```
Это read-modify-write без транзакции. При двух параллельных сообщениях оба читают `messages_used = 5`, оба пишут `6`. Счётчик не увеличивается корректно.

**Impact:** Клиенты могут превысить лимит сообщений без оплаты. При активном использовании (несколько клиентов одновременно) — реальная потеря денег.

**Решение:** SQL-инкремент через RPC или прямой SQL:
```typescript
// Вместо .update({ messages_used: subscription.messages_used + 1 })
await supabase.rpc('increment_messages_used', { sub_id: subscription.id })
```

SQL функция:
```sql
CREATE OR REPLACE FUNCTION increment_messages_used(sub_id uuid)
RETURNS void LANGUAGE sql SECURITY DEFINER AS $$
  UPDATE subscriptions
  SET messages_used = messages_used + 1,
      updated_at = now()
  WHERE id = sub_id;
$$;
```

**Effort: S (30 минут)**

### 🟡 ВАЖНО-5: Нет ограничения длины входящего сообщения

**Проблема:** Злоумышленник может отправить сообщение в 10 000 символов. Это раздует input tokens до ~2 500 tokens/запрос вместо ~50. При 1 000 сообщений/мес стоимость вырастет в 50 раз.

**Impact:** Финансовые потери, исчерпание Anthropic лимита ($30/мес).

**Решение:** В `src/lib/telegram/bot-factory.ts:200`:
```typescript
bot.on('message:text', async (ctx) => {
  const text = ctx.message.text
  if (text.length > 1000) {
    await ctx.reply('Сообщение слишком длинное. Пожалуйста, напишите короче.')
    return
  }
  // ...
})
```

**Effort: S (10 минут)**

### 🟡 ВАЖНО-6: Slot generation timezone bug

**Проблема:** В `src/lib/telegram/bot-factory.ts:96`:
```typescript
const slotMs = new Date(`${dateStr}T${String(slotHour).padStart(2, '0')}:${String(slotMin).padStart(2, '0')}:00`).getTime()
```
`new Date('2026-03-01T10:00:00')` парсится как **UTC**, не как local time бизнеса. Для бизнеса в Москве (UTC+3) слот "10:00" будет показан как "13:00 МСК". Клиенты получают неправильное время.

**Impact:** Клиенты записываются на неправильное время. Критично для продукта.

**Решение:** Использовать правильное преобразование timezone:
```typescript
// Создать дату в timezone бизнеса
const slotIso = `${dateStr}T${String(slotHour).padStart(2, '0')}:${String(slotMin).padStart(2, '0')}:00`
// Конвертировать из tz в UTC
const slotMs = new Date(
  new Date(slotIso).toLocaleString('en-US', { timeZone: 'UTC' })
).getTime() - getTimezoneOffset(tz, new Date(slotIso))
```
Или использовать библиотеку `date-fns-tz` для корректной работы с timezone.

**Effort: M (2-3 часа)**

## 3. UX/UI АУДИТ (UX/UI Audit)

### Dashboard — что хорошо, что плохо

**Хорошо:**
- Онбординг-чеклист (5 шагов) — отличная идея, исчезает когда всё готово
- Параллельные запросы (4 запроса одновременно) — быстро
- StatCard компоненты — чистый дизайн
- Зелёный баннер "Бот работает" — даёт уверенность

**Плохо:**
- **Нет данных о подписке на главной** — пользователь не видит сколько сообщений осталось без перехода в /billing
- **"Записей сегодня" считает все статусы** — включая cancelled. Нужно фильтровать по `confirmed + completed`
- **"Сообщений за месяц"** — считает только `role = 'user'`, но не показывает лимит. Нужно: "127 / 1000"
- **Нет быстрых действий** — нельзя создать запись вручную с дашборда
- **Нет последних записей** — владелец хочет видеть "что происходит прямо сейчас"

**Рекомендации:**
1. Добавить мини-виджет подписки на дашборд (использовано X/Y сообщений)
2. Добавить "Последние 5 записей" на дашборд
3. Исправить счётчик "Записей сегодня" (только confirmed + completed)
4. Показывать "X / Y сообщений" вместо просто числа

### Landing page — реальная боль vs. текущий текст

## 4. АРХИТЕКТУРА (Architecture Review)

### Что solid

**Хорошо спроектировано:**
- **Multi-tenant routing** через `?id=businessId` — элегантно, масштабируемо
- **React cache()** в `queries.ts` — дедупликация запросов layout + page
- **Параллельная загрузка контекста** (`Promise.all` в `bot-factory.ts:342-380`) — 5 запросов одновременно
- **RLS на всех таблицах** — безопасность на уровне БД
- **Webhook verification** (Telegram secret + YooKassa re-fetch) — правильно
- **Structured logging** (`[bot:BIZID]` prefix) — удобно для дебага
- **Tool Use для создания записей** — правильный подход, не парсинг текста
- **Unique partial index** для предотвращения двойного бронирования (`004_sprint7.sql:22-24`)

### Что нужно рефакторить

**1. Clients page — N+1 проблема:**
```typescript
// clients/page.tsx:46-57
// Загружает ВСЕ сообщения бизнеса для подсчёта
const { data: messageCounts } = await supabase
  .from('messages')
  .select('client_id')
  .eq('business_id', business.id)
// При 1000 клиентах × 100 сообщений = 100 000 строк в памяти
```

**Решение:** SQL GROUP BY:
```sql
SELECT client_id, COUNT(*) as message_count
FROM messages
WHERE business_id = $1
GROUP BY client_id
```

**2. Analytics — группировка в JS:**
```typescript
// analytics/page.tsx:87-122
// Загружает все записи месяца, группирует в JS
const serviceCountMap: Record<string, number> = {}
for (const booking of monthBookings ?? []) { ... }
```

**Решение:** SQL GROUP BY с JOIN:
```sql
SELECT s.name, COUNT(*) as count
FROM bookings b
JOIN services s ON s.id = b.service_id
WHERE b.business_id = $1 AND b.scheduled_at >= $2
GROUP BY s.name
ORDER BY count DESC
LIMIT 3
```

**3. Bot cache — per-instance:**
```typescript
// bot-factory.ts:9
const botCache = new Map<string, Bot>()
```
При 10+ клиентах и нескольких Vercel instances каждый instance инициализирует все боты заново. Это не критично, но добавляет latency.

### Performance bottlenecks

| Проблема | Где | Impact | Решение |
|----------|-----|--------|---------|
| N+1 в clients page | `clients/page.tsx:46` | При 200+ клиентах | SQL GROUP BY |
| JS grouping в analytics | `analytics/page.tsx:87` | При 500+ записей/мес | SQL GROUP BY |
| Bot cold start (200-500ms) | `bot-factory.ts:141` | Первый запрос после cold start | Нет простого решения |
| Нет кэширования контекста | `bot-factory.ts:342` | 5 DB запросов на каждое сообщение | Redis cache (при 20+ клиентах) |

### Render strategy — оптимальна ли?

**Текущая стратегия:**
- Dashboard pages: **SSR** (Server Components) — правильно, данные меняются часто
- Landing page: **SSR** — можно сделать **SSG** для лучшей производительности
- API routes: `force-dynamic` — правильно для webhook

**Рекомендация:** Landing page (`src/app/page.tsx`) не имеет динамических данных. Добавить:
```typescript
export const revalidate = 3600 // ISR: обновлять раз в час
```
Это ускорит TTFB для новых посетителей.

### Caching opportunities

1. **Business context** (services, masters, knowledge) — меняется редко. Можно кэшировать в Redis на 5 минут. Экономия: 3 из 5 DB запросов на каждое сообщение.
2. **Landing page** — ISR с revalidate 3600
3. **Subscription status** — кэшировать на 1 минуту (сейчас читается при каждом сообщении)

### Edge cases в bot-factory.ts

**1. Webhook идемпотентность:**
Telegram повторяет webhook при таймауте (>5 секунд). Если AI занял 6 секунд, Telegram отправит webhook повторно. Второй запрос создаст дублирующую запись. Уникальный индекс `bookings_no_double_booking` частично защищает (только для одного мастера+слота), но не для записей без мастера.

**Решение:** Хранить `telegram_update_id` и проверять на дубликаты.

**2. Slot generation timezone:**
Описано в КРИТИЧНО-6. Слоты генерируются в UTC, показываются как local time — несоответствие.

**3. Master selection fallback:**
```typescript
// engine.ts:178
: ctx.masters[0] ?? null
```
Если мастер не указан — берётся первый из списка. Это может быть неправильно если у первого мастера нет свободных слотов.

**4. Bot cache при смене токена:**
Если владелец меняет токен бота в настройках, старый бот остаётся в `botCache`. Новые сообщения будут обрабатываться старым ботом до перезапуска instance.

**Решение:** При сохранении нового токена — инвалидировать кэш:
```typescript
botCache.delete(businessId)
```

**5. Vercel timeout 10s:**
Claude Haiku обычно отвечает за 1-3 секунды. Но при высокой нагрузке на Anthropic API — может занять 8-9 секунд. Если превысит 10s — Vercel вернёт 504, Telegram повторит webhook.

### Текущие меры защиты

| Мера | Реализация | Оценка |
|------|-----------|--------|
| Telegram webhook secret | `x-telegram-bot-api-secret-token` header | ✅ Хорошо |

| Bot token encryption | AES-256-CBC | ✅ Достаточно для MVP |
| RLS на всех таблицах | Supabase RLS policies | ✅ Хорошо |
| Cron secret | `x-cron-secret` header | ✅ Хорошо |
| Rate limiting | In-memory, 10/мин | ⚠️ Не работает multi-instance |
| Auth | Supabase Auth JWT | ✅ Хорошо |
| Service Role Key | Только в Vercel secrets | ✅ Хорошо |

### Уязвимости и риски

**🔴 КРИТИЧНО: test-activate endpoint**
- Файл: `src/app/api/billing/test-activate/route.ts`
- Риск: Активация подписки без оплаты
- Blast radius: Финансовые потери, компрометация биллинга
- Решение: Удалить или заблокировать в production

**🔴 КРИТИЧНО: Нет ограничения длины сообщения**
- Файл: `src/lib/telegram/bot-factory.ts:200`
- Риск: Token flooding — злоумышленник отправляет 10 000-символьные сообщения
- Blast radius: Исчерпание Anthropic лимита ($30/мес), финансовые потери
- Решение: Ограничить до 1000 символов

**🟡 СРЕДНЕ: Фиксированный salt в шифровании**
- Файл: `src/lib/crypto.ts:9` — `scryptSync(secret, 'vika-token-v1', 32)`
- Риск: Если `BOT_TOKEN_ENCRYPTION_KEY` утечёт — все токены расшифровываются одним ключом
- Blast radius: Компрометация всех Telegram-ботов всех клиентов
- Решение: Уникальный salt на каждый токен (хранить рядом с зашифрованным значением)

**🟡 СРЕДНЕ: Plaintext fallback при расшифровке**
- Файл: `src/lib/crypto.ts:24`
- Риск: Токены, сохранённые до шифрования, хранятся в открытом виде в БД
- Blast radius: Компрометация старых токенов при утечке БД
- Решение: Убедиться что все токены перешифрованы, убрать fallback

**🟡 СРЕДНЕ: Rate limiter не работает multi-instance**
- Файл: `src/lib/telegram/rate-limiter.ts:2`
- Риск: Пользователь может отправить 10 сообщений на instance A и 10 на instance B
- Blast radius: Превышение AI лимитов, финансовые потери
- Решение: Upstash Redis при 20+ клиентах

**🟡 СРЕДНЕ: Нет IP rate limiting на webhook**
- Файл: `src/app/api/telegram/webhook/route.ts`
- Риск: DDoS на webhook endpoint
- Blast radius: Vercel timeout, финансовые потери
- Решение: Vercel Edge Config или Cloudflare WAF

**🟢 НИЗКО: Нет CSRF protection на Server Actions**
- Next.js 15 имеет встроенную CSRF защиту для Server Actions (Origin header check)
- Риск минимален, но стоит проверить конфигурацию

### Что происходит при компрометации (blast radius)

**Сценарий 1: Утечка `SUPABASE_SERVICE_ROLE_KEY`**
- Злоумышленник получает полный доступ к БД (bypass RLS)
- Может читать все данные клиентов, токены ботов, сообщения
- Может изменять подписки, активировать бесплатно
- **Митигация:** Ротация ключа в Supabase dashboard + Vercel env vars

**Сценарий 2: Утечка `BOT_TOKEN_ENCRYPTION_KEY`**
- Злоумышленник расшифровывает все Telegram-токены из БД
- Может управлять ботами от имени клиентов
- **Митигация:** Ротация ключа + перешифровка всех токенов

**Сценарий 3: Утечка `ANTHROPIC_API_KEY`**
- Злоумышленник использует API за ваш счёт
- Hard cap $30/мес ограничивает ущерб
- **Митигация:** Ротация ключа в Anthropic Console

**Сценарий 4: Компрометация Supabase БД**
- Утечка персональных данных клиентов (имена, Telegram ID, телефоны)
- Нарушение 152-ФЗ, штрафы до 500 000 ₽
- **Митигация:** Supabase Pro с PITR бэкапами, уведомление РКН

### Backup strategy

**Текущее состояние:**
- Supabase Free: ежедневные бэкапы, **1 день retention** — катастрофически мало
- Нет point-in-time recovery
- Нет тестирования восстановления

**Рекомендации:**
1. При 5+ платящих клиентах: Supabase Pro ($25/мес) → 7-дневный PITR
2. Настроить pg_dump экспорт раз в неделю в S3/Yandex Object Storage
3. Тестировать восстановление раз в месяц

### Secrets management

**Текущее состояние:** Все секреты в Vercel env vars — приемлемо для MVP.

**Рекомендации:**
1. Использовать разные секреты для dev/prod окружений
2. Ротировать `TELEGRAM_WEBHOOK_SECRET` и `CRON_SECRET` раз в квартал
3. Добавить мониторинг аномального использования Anthropic API

### Input validation

**Хорошо:** Zod используется в формах (settings, services, masters).

**Плохо:**
- Нет валидации длины сообщения в боте
- Нет санитизации `notes` поля при создании записи
- `preferred_datetime` от AI не валидируется строго (только `new Date()` parse)

### Рекомендации по безопасности (приоритизированные)

1. **Немедленно:** Удалить `test-activate` или заблокировать в production
2. **Немедленно:** Добавить ограничение длины сообщения (1000 символов)

## 11. MAX MESSENGER — ИНТЕГРАЦИЯ (MAX Messenger Integration Analysis)

> Исследование проведено: 2026-02-27

### Что такое MAX

**MAX** (ранее VK Teams / Mail.ru Messenger) — мессенджер от VK Group, запущенный в 2024 году как ребрендинг корпоративного мессенджера VK Teams. Позиционируется как российская альтернатива Telegram с акцентом на:
- Интеграцию с экосистемой VK (ВКонтакте, Mail.ru, Одноклассники)
- Корпоративные функции (рабочие пространства, каналы)
- Соответствие российскому законодательству (серверы в РФ)

**Аудитория (оценка 2025-2026):**
- Активных пользователей: ~15-20 млн (преимущественно пользователи ВКонтакте)
- Основная аудитория: 18-35 лет, Россия и СНГ
- Для сравнения: Telegram в России — ~50-60 млн активных пользователей

### Bot API MAX — техническая оценка

**Статус Bot API:**
MAX имеет Bot API, задокументированный через developer.vk.com и официальный портал MAX. API основан на VK Teams Bot API (`https://teams.vk.com/botapi/`), который был переименован вместе с продуктом.

**Ключевые характеристики API:**

| Параметр | MAX Bot API | Telegram Bot API |
|----------|-------------|-----------------|
| Протокол | HTTP REST + Webhooks | HTTP REST + Webhooks |
| Формат | JSON | JSON |
| Polling | Long polling (`/events/get`) | getUpdates |
| Webhook | Поддерживается | Поддерживается |
| Inline keyboards | Поддерживается | Поддерживается |
| Callback queries | Поддерживается | Поддерживается |
| File upload | Поддерживается | Поддерживается |
| Markdown | Частично | Полная поддержка |
| Tool Use / Function Calling | Нет (это AI-фича, не Bot API) | Нет (это AI-фича) |

**Совместимость с GrammY:**
GrammY — это библиотека специфичная для Telegram Bot API. Она **не совместима** с MAX Bot API напрямую. Причины:
1. Разные endpoint URL (`api.telegram.org` vs MAX API endpoint)
2. Разные форматы объектов (Update, Message, Chat)
3. Разные методы аутентификации
4. GrammY использует Telegram-специфичные типы TypeScript

**Что потребуется для интеграции MAX:**

```
Вариант A: Отдельный адаптер (рекомендуется)
  - Написать MAX Bot adapter (аналог GrammY, но для MAX API)
  - Создать абстракцию над обоими API (общий интерфейс)
  - Переписать bot-factory.ts для поддержки обоих провайдеров
  - Effort: XL (2-4 недели)

Вариант B: Использовать существующую библиотеку
  - Проверить наличие npm-пакетов для MAX/VK Teams Bot API
  - Известные пакеты: @vkteams/bot-sdk (официальный, но устаревший)
  - Effort: L (1-2 недели)

Вариант C: Прямые HTTP запросы
  - Написать тонкий wrapper над MAX HTTP API
  - Без типизации, без middleware
  - Effort: M (1 неделя)
```

### Ключевые отличия от Telegram Bot API

**Структурные отличия:**

1. **Идентификаторы пользователей:** MAX использует строковые `userId` вида `user@domain`, Telegram — числовые `chat_id`
2. **Чаты:** В MAX нет понятия "личный чат с ботом" в том же смысле — боты работают в "группах" или через прямые сообщения
3. **Webhook формат:** Разная структура Update объекта
4. **Медиа:** Разные форматы для загрузки файлов
5. **Команды:** Нет стандартного `/start` — нужна кастомная логика приветствия

### Оценка целесообразности интеграции MAX

**Аргументы ЗА:**
1. **Диверсификация риска** — если Telegram заблокируют, MAX — готовая альтернатива
2. **Российская аудитория** — MAX растёт в России, особенно среди молодёжи
3. **Государственная поддержка** — VK Group имеет хорошие отношения с регуляторами
4. **Серверы в РФ** — решает проблему 152-ФЗ
5. **Уникальное УТП** — "работает и в Telegram, и в MAX" — конкурентное преимущество

**Аргументы ПРОТИВ:**
1. **Малая аудитория** — 15-20 млн vs 50-60 млн у Telegram. Целевая аудитория (малый бизнес) преимущественно в Telegram
2. **Высокая стоимость разработки** — XL effort при текущем соло-основателе
3. **Нестабильный API** — MAX активно развивается, API может меняться
4. **Нет экосистемы** — нет аналога GrammY, нет сообщества разработчиков ботов
5. **Неизвестная конверсия** — неясно, используют ли малые бизнесы MAX для общения с клиентами

**Вывод:**

> **MAX — это страховка, а не приоритет.** Интегрировать MAX нужно только после достижения 50+ платящих клиентов в Telegram, когда есть ресурсы на разработку и реальный спрос от клиентов. До этого — мониторить рост MAX и готовить архитектурную абстракцию.

### Рекомендуемый план интеграции MAX

**Сейчас (0-50 клиентов):**
- Не интегрировать MAX
- Подготовить архитектуру: вынести Telegram-специфичный код в `src/lib/telegram/` (уже сделано)
- Добавить поле `messenger_type` в таблицу `clients` (миграция, 30 минут)

**При 50+ клиентах:**
- Провести опрос клиентов: "Нужен ли вам MAX?"
- Если >20% говорят "да" — начать разработку адаптера
- Effort: L-XL (2-4 недели)

**При реальной угрозе блокировки Telegram:**
- Ускорить интеграцию MAX как приоритет P0
- Параллельно рассмотреть WhatsApp Business API

## 12. ПРОДУКТОВЫЙ АНАЛИЗ — ПЕРСПЕКТИВА КЛИЕНТА (Client Perspective Analysis)

> Клиент = конечный пользователь, который записывается через бота

### Что VIKA решает для клиента

**Реальные боли, которые закрывает VIKA:**

1. **Запись в любое время** — клиент может записаться в 23:00, не ждать утра
2. **Мгновенный ответ** — не нужно ждать, пока владелец прочитает сообщение
3. **Видит доступные слоты** — не нужно угадывать "а когда свободно?"
4. **Напоминания** — не забудет о записи (24h и 1h)
5. **Отмена через бота** — `/mybookings` + кнопка отмены без звонка

### Что VIKA НЕ решает или создаёт проблемы

**Критические проблемы для клиента:**

1. **Нет подтверждения в реальном времени**
   - Клиент создаёт запись → статус `pending` → ждёт подтверждения владельца
   - Если владелец не подтвердит за 2-3 часа — клиент не знает, записан ли он
   - **Боль:** "Я записался или нет? Почему нет ответа?"
   - **Решение:** Автоподтверждение (если слот свободен — сразу `confirmed`) или SLA уведомление ("Владелец подтвердит в течение 2 часов")

2. **Нет выбора конкретного мастера**
   - AI назначает первого доступного мастера (`ctx.masters[0] ?? null`)
   - Клиент хочет к конкретному мастеру, но бот не спрашивает
   - **Боль:** "Я хочу к Ане, а не к кому попало"
   - **Решение:** AI должен спрашивать "К какому мастеру?" если мастеров несколько

3. **Нет онлайн-оплаты**
   - Клиент записывается, но не платит заранее
   - Высокий no-show rate (клиенты не приходят)
   - **Боль для бизнеса:** потерянное время
   - **Решение:** Предоплата через YooKassa при записи

4. **Нет истории записей в удобном виде**
   - `/mybookings` показывает только текущие записи
   - Нет истории прошлых визитов
   - **Боль:** "Когда я последний раз был? Что делал?"

5. **Нет возможности перенести запись**
   - Клиент может только отменить, но не перенести
   - Нужно отменить и записаться заново — неудобно
   - **Боль:** "Хочу перенести на другой день, а не отменять"

**Важные проблемы:**

6. **Нет согласия на обработку ПДн при первом контакте**
   - Клиент пишет боту и не знает, что его данные сохраняются
   - Юридический риск по 152-ФЗ
   - **Решение:** Приветственное сообщение с ссылкой на политику конфиденциальности

7. **Бот не знает, что делать при нестандартных запросах**
   - "Можно ли прийти с ребёнком?" — бот не знает
   - "Есть ли парковка?" — бот не знает (если не добавлено в FAQ)
   - **Боль:** Клиент получает "Я не знаю" и уходит
   - **Решение:** Улучшить fallback — "Я не знаю, но владелец ответит вам в ближайшее время"

8. **Нет мультиязычности**
   - Бот отвечает только на русском
   - В крупных городах есть клиенты, говорящие на других языках
   - **Решение:** Определять язык по `language_code` в Telegram профиле

9. **Нет уведомления об изменении статуса в реальном времени**
   - Если владелец отменяет запись — клиент получает уведомление
   - Но если владелец переносит запись вручную — клиент не знает
   - **Решение:** Уведомление при любом изменении статуса

**Мелкие проблемы:**

10. **Нет подтверждения адреса/локации**
    - Клиент записался, но не знает адрес
    - **Решение:** Добавить адрес в подтверждение записи

11. **Нет возможности оставить отзыв**
    - После визита бот не спрашивает "Как всё прошло?"
    - **Решение:** Автоматическое сообщение через 2 часа после записи

### Accessibility (доступность)

**Текущие проблемы:**
- Бот не поддерживает голосовые сообщения (только текст)
- Нет поддержки кнопок для выбора слота (только текстовый диалог)
- Длинные текстовые ответы сложно читать на мобильном

**Рекомендации:**
1. Добавить inline keyboard для выбора даты/времени (Telegram Mini App или inline buttons)
2. Обрабатывать голосовые сообщения (Whisper API для транскрипции)
3. Сократить длину ответов бота — максимум 3-4 строки

### Идеальный клиентский путь (как должно быть)

```
Клиент пишет "Хочу записаться"
  → Бот: "К какому мастеру? [Аня] [Маша] [Любой]"
  → Клиент выбирает
  → Бот: "На какую услугу? [Стрижка 800р] [Окрашивание 2500р]"
  → Клиент выбирает
  → Бот: "Выберите время: [Пн 10:00] [Пн 14:00] [Вт 11:00]"
  → Клиент выбирает
  → Бот: "Отлично! Записала вас к Ане на стрижку в понедельник в 10:00.
          Адрес: ул. Ленина, 15. Напомню за 24 часа и за 1 час.
          [Отменить запись]"
  → Клиент получает подтверждение СРАЗУ (автоподтверждение)
```

**Текущий путь (как есть):**
```
Клиент пишет "Хочу записаться"
  → Бот: длинный текстовый ответ с вопросами
  → Клиент отвечает текстом
  → Бот создаёт запись со статусом "pending"
  → Клиент ждёт подтверждения от владельца (может часами)
```

## 13. ПРОДУКТОВЫЙ АНАЛИЗ — ПЕРСПЕКТИВА ВЛАДЕЛЬЦА БИЗНЕСА (Business Owner Perspective)

> Владелец = тот, кто платит за VIKA и управляет ботом

### Что VIKA решает для владельца

**Реальные боли, которые закрывает VIKA:**

1. **Экономия времени на переписке** — 30-60 минут в день
2. **Запись 24/7** — клиенты записываются ночью, в выходные
3. **Автоматические напоминания** — снижение no-show
4. **Централизованный дашборд** — все записи в одном месте
5. **История клиентов** — кто приходил, как часто, что заказывал
6. **Уведомления о новых записях** — не нужно постоянно проверять

### Что VIKA НЕ решает или создаёт проблемы

**Критические проблемы для владельца:**

1. **Нет Google Calendar / Яндекс Календарь синхронизации**
   - Владелец ведёт расписание в Google Calendar
   - VIKA создаёт записи в своей БД, но не синхронизирует с Calendar
   - **Боль:** "Мне нужно смотреть в два места"
   - **Решение:** Google Calendar API интеграция (двусторонняя синхронизация)
   - **Effort:** L (2-3 недели)

2. **Нет мобильного приложения / PWA**
   - Владелец управляет бизнесом с телефона
   - Дашборд не оптимизирован для мобильных (sidebar проблема)
   - **Боль:** "Я не могу нормально работать с телефона"
   - **Решение:** PWA или мобильная адаптация (уже в плане)

3. **Нет ручного создания записи**
   - Клиент позвонил по телефону — владелец не может создать запись в VIKA
   - Нужно идти в дашборд и... нет кнопки "Создать запись"
   - **Боль:** "Мне позвонили, я хочу записать вручную"
   - **Решение:** Форма создания записи в дашборде

4. **Нет блокировки времени**
   - Владелец уходит в отпуск — нет способа заблокировать даты
   - Бот продолжает предлагать слоты в период отпуска
   - **Боль:** "Я в отпуске, а бот записывает клиентов"
   - **Решение:** Функция "Выходные дни" / блокировка периодов

5. **Нет аналитики выручки**
   - Дашборд показывает количество записей, но не деньги
   - Владелец не знает, сколько заработал за месяц
   - **Боль:** "Сколько я заработал в этом месяце?"
   - **Решение:** Добавить поле `price` к записи, считать выручку

6. **Нет WhatsApp / Instagram интеграции**
   - Многие клиенты пишут в WhatsApp или Instagram DM
   - VIKA работает только в Telegram
   - **Боль:** "Мои клиенты не все в Telegram"
   - **Решение:** WhatsApp Business API (дорого, ~$50/мес), Instagram API (ограниченный)

**Важные проблемы:**

7. **Нет экспорта данных**
   - Нельзя выгрузить список клиентов в Excel/CSV
   - **Боль:** "Хочу сделать рассылку по базе"
   - **Решение:** Экспорт CSV (в плане Фазы 2)

8. **Нет массовых уведомлений**
   - Нельзя отправить сообщение всем клиентам ("Акция на этой неделе!")
   - **Боль:** "Хочу сообщить клиентам об акции"
   - **Решение:** Broadcast функция (требует согласия клиентов по 152-ФЗ)

9. **Нет настройки автоподтверждения**
   - Все записи требуют ручного подтверждения
   - Активный бизнес тратит время на подтверждение каждой записи
   - **Боль:** "Зачем мне подтверждать каждую запись?"
   - **Решение:** Настройка "Автоподтверждение" в settings

10. **Нет мультибота (несколько ботов для одного бизнеса)**
    - Если у бизнеса несколько локаций — нужен отдельный аккаунт для каждой
    - **Боль:** "У меня 2 точки, мне нужно 2 аккаунта?"
    - **Решение:** Поддержка нескольких ботов в одном аккаунте

11. **Нет интеграции с YCLIENTS/Dikidi**
    - Бизнес уже использует YCLIENTS — не хочет переходить полностью
    - **Боль:** "Я хочу только бота, но оставить YCLIENTS для расписания"
    - **Решение:** API интеграция с YCLIENTS (сложно, но возможно)

**Мелкие проблемы:**

12. **Нет настройки приветственного сообщения**
    - Бот использует стандартное приветствие
    - Владелец хочет персонализировать: "Привет! Я бот студии Аня Нейлс"
    - **Решение:** Поле "Приветственное сообщение" в settings

13. **Нет статистики по источникам клиентов**
    - Откуда пришли клиенты? Из Instagram? По рекомендации?
    - **Решение:** UTM-параметры в ссылке на бота

14. **Нет уведомлений об отменах клиентом**
    - Если клиент отменяет запись — владелец должен получать уведомление
    - Нужно проверить и убедиться, что это реализовано

### Сравнение с конкурентами — что нужно для переключения с YCLIENTS/Dikidi

**Почему владелец НЕ переключится с YCLIENTS:**
1. YCLIENTS имеет виджет на сайте + приложение для клиентов

4. AI-диалог лучше, чем форма на сайте

- Зарплатный модуль — сложно, не приоритет
- Google Calendar sync — важно, реалистично

**Вывод:** VIKA не заменит YCLIENTS для среднего/крупного бизнеса. Но для малого бизнеса (1-3 мастера) — полноценная замена при добавлении онлайн-оплаты и Calendar sync.

- **Стоимость:** $0 (только время)

**3. Партнёрства с поставщиками**

- Они уже имеют базу клиентов (малый бизнес)
- **Механика:** Партнёрская программа — поставщик рекомендует VIKA, получает % от подписки

- Конкуренция низкая (нишевые запросы)
- **Стоимость:** Время на написание статей

**5. Прямые продажи в профессиональных сообществах**
- Форумы барберов, nail-мастеров
- Личные сообщения владельцам (не спам — персонализированный питч)
- **Конверсия:** ~5-10% при правильном подходе

**Текущий ров (слабый):**
- Telegram-first подход (конкуренты не фокусируются на Telegram)

## 15. РИСК БЛОКИРОВКИ TELEGRAM (Telegram Block Risk Analysis)

### Насколько реален риск?

**История:**
- 2018: Telegram заблокирован в России по решению Роскомнадзора
- 2020: Блокировка снята — Telegram согласился сотрудничать с ФСБ (предоставлять данные по запросу)
- 2022-2025: Telegram активно используется в России, включая государственными структурами

**Текущая ситуация (2025-2026):**
- Telegram де-факто легализован в России
- Государственные каналы активно используют Telegram
- Павел Дуров арестован во Франции (август 2024) — создал неопределённость
- Telegram начал сотрудничать с властями ряда стран

**Оценка риска:**

```
Вероятность полной блокировки Telegram в России (2026): ~10-15%
Вероятность частичной блокировки (замедление): ~20-25%
Вероятность сохранения статус-кво: ~60-70%
```

**Факторы, снижающие риск:**
1. Telegram используют миллионы россиян — политически сложно заблокировать
2. Государственные структуры сами используют Telegram
3. Telegram уже сотрудничает с российскими властями
4. Экономические потери от блокировки для малого бизнеса

**Факторы, повышающие риск:**
1. Прецедент 2018 года — уже блокировали
2. Арест Дурова создал прецедент давления
3. Политическая нестабильность
4. Конкуренция с российскими мессенджерами (VK, MAX)

### Стратегия митигации

**Уровень 1 — Немедленно (без затрат):**
- Добавить поле `messenger_type` в таблицу `clients` (30 минут)
- Архитектурно изолировать Telegram-специфичный код (уже сделано в `src/lib/telegram/`)
- Мониторить новости о регуляторных изменениях

**Уровень 2 — При 50+ клиентах:**
- Разработать MAX адаптер (см. раздел 11)
- Добавить SMS-напоминания как резервный канал (Twilio или SMSC.ru)
- Добавить email-напоминания

**Уровень 3 — При реальной угрозе блокировки:**
- Экстренная интеграция MAX (2-4 недели)
- Уведомить всех клиентов о переходе на MAX
- Предложить миграцию данных

**Уровень 4 — При фактической блокировке:**
- Переключить всех клиентов на MAX
- Рассмотреть WhatsApp Business API
- Рассмотреть собственный мессенджер (нереалистично для MVP)

## 16. СТРАТЕГИЯ МЕССЕНДЖЕРОВ (Multi-Messenger Strategy)

### Текущее состояние

VIKA работает **только в Telegram**. Это одновременно сила (фокус) и слабость (зависимость).

### Анализ мессенджеров для интеграции

| Мессенджер | Аудитория в РФ | Bot API | Сложность | Приоритет |
|------------|----------------|---------|-----------|-----------|
| Telegram | 50-60 млн | Отличный | — (уже есть) | Текущий |
| WhatsApp | 60-70 млн | Business API | Высокая | P2 |
| VK (ВКонтакте) | 70-80 млн | VK Bot API | Средняя | P2 |
| MAX | 15-20 млн | Есть | Высокая | P1 (страховка) |
| Viber | 20-30 млн | Chatbot API | Средняя | P3 |
| Instagram DM | 40-50 млн | Ограниченный | Очень высокая | P3 |

### Детальный анализ каждого мессенджера

#### WhatsApp Business API

**Плюсы:**
- Самая большая аудитория в России (60-70 млн)
- Многие клиенты предпочитают WhatsApp
- Официальный Business API с хорошей документацией

**Минусы:**
- Стоимость: ~$0.05-0.15 за разговор (дорого при большом объёме)
- Требует верификации бизнеса (1-2 недели)
- Нужен номер телефона (не анонимно)
- Meta (Facebook) — западная компания, риски санкций
- Сложная интеграция (нужен BSP — Business Solution Provider)

**Вывод:** Высокий потенциал, но высокая стоимость и сложность. Рассмотреть при 100+ клиентах.

#### VK (ВКонтакте) Bot API

**Плюсы:**
- Огромная аудитория (70-80 млн в России)
- Российская компания, нет санкционных рисков
- Хорошая документация VK Bot API
- Бесплатный API
- Многие малые бизнесы уже имеют страницу ВКонтакте

**Минусы:**
- Аудитория ВКонтакте старше (35+), не все используют мессенджер
- VK API менее удобен, чем Telegram Bot API
- Нет аналога GrammY для VK

**Вывод:** Хороший вариант для расширения аудитории. Средняя сложность интеграции.

#### MAX (VK Teams)

**Плюсы:**
- Российская компания, серверы в РФ
- Растущая аудитория
- Страховка от блокировки Telegram

**Минусы:**
- Малая аудитория (15-20 млн)
- Нестабильный API
- Нет экосистемы разработчиков

**Вывод:** Приоритет P1 как страховка, не как основной канал роста.

### Рекомендуемая стратегия мессенджеров

```
Фаза 1 (сейчас — 50 клиентов):

```
