## Sprint 5 — Path B Booking (NEXT)

### Концепция
AI собирает данные → создаёт `pending` запись → владелец подтверждает в дашборде.
Не нужно знать занятость — владелец проверяет вручную. Честно позиционировать как бета.

### Задачи

#### 5.1 Claude Tool Use в AI движке
- Добавить инструмент `create_booking` в `engine.ts`
- Параметры: `service_name`, `master_name`, `preferred_datetime` (ISO string), `notes`
- AI вызывает инструмент когда клиент назвал услугу + время
- Функция резолвит service_id / master_id по имени из контекста
- Создаёт `bookings` со статусом `pending`
- Отвечает клиенту: "Заявка принята, ожидайте подтверждения"

#### 5.2 Передать занятые слоты в промпт
- При вызове AI добавлять к контексту: список `pending`/`confirmed` записей на следующие 7 дней
- Формат: "Занято: ПТ 14:00 (Стрижка), СБ 10:00-12:00 (2 записи)"
- AI говорит клиенту о занятости самостоятельно

#### 5.3 Управление статусом в дашборде
- Кнопки "Подтвердить" / "Отменить" в `/bookings`
- Server action `updateBookingStatus(bookingId, status)`
- При подтверждении — отправить Telegram сообщение клиенту через бот бизнеса
- Фильтр: предстоящие / прошедшие / все

#### 5.4 Уведомление владельца
- Уже есть для intent='booking' — расширить на создание записи
- Сообщение: "📅 Новая запись: [клиент] хочет [услугу] [дата/время]. Подтвердите в панели."

## Критические проблемы производительности

### Проблема 1: Медленные сохранения (ГЛАВНАЯ)

**Причина:** Каждый server action делает 3 последовательных round-trip:
1. `supabase.auth.getUser()` — ~150ms (сеть до Supabase Auth)
2. `getBusiness()` — ~100ms (запрос в БД)
3. Сам мутирующий запрос — ~80ms

Итого: ~330ms на каждое сохранение.

**Решение:** Передавать `businessId` как hidden form field.
RLS автоматически защищает от подмены — запрос упадёт если businessId чужой.
Убрать `getBusiness()` из actions, оставить только в page components.

**Файлы:** `actions/{services,masters,knowledge,business}.ts`
**Эффект:** Сохранение ускорится с ~330ms до ~80ms

### Проблема 2: Каждая навигация — новый SSR рендер

**Причина:** Все страницы `force-dynamic`, нет кэширования на уровне Next.js.
При переходе `/services` → `/masters` — оба делают `getCurrentUser()` + `getBusiness()`.

**Решение краткосрочное:** `React cache()` уже есть — deduplicates within render. Этого достаточно для MVP.

**Решение долгосрочное:** Вынести статичные данные (services, masters) в SWR/TanStack Query на клиенте с optimistic updates.

### Проблема 3: Отсутствующие индексы в БД

Запросы `WHERE business_id = X` делают full table scan на таблицах без индексов.

```sql
-- Добавить в следующую миграцию:
CREATE INDEX idx_clients_business ON public.clients(business_id);
CREATE INDEX idx_services_business ON public.services(business_id);
CREATE INDEX idx_masters_business ON public.masters(business_id);
CREATE INDEX idx_knowledge_business ON public.knowledge_items(business_id);
CREATE INDEX idx_messages_client ON public.messages(client_id, created_at DESC);
```

## Безопасность

### Хранение данных клиентов

**Что хранится:**
- `telegram_user_id` (число) — публичный ID Telegram
- `first_name`, `last_name` — из публичного Telegram профиля
- `telegram_username` — публичный
- `phone` — заполняется только если клиент сам передал в разговоре

**Риск при взломе БД (Supabase breach):**
- Клиентские данные открыты (имена, Telegram ID) — это персональные данные по 152-ФЗ
- Токены ботов **зашифрованы** AES-256-CBC — без `BOT_TOKEN_ENCRYPTION_KEY` из env не расшифровать
- Платёжных данных нет — YooKassa хранит сама (PCI-DSS)

**Действия при взломе:**
1. Ротировать `BOT_TOKEN_ENCRYPTION_KEY` → все токены невалидны, бизнесы перегенерируют
2. Уведомить пользователей
3. Supabase support ticket для анализа

**Текущие слабые места:**
- Фиксированный salt в `crypto.ts` — принять как допустимо для MVP (безопасность держится на секретности env key)
- Service Role Key в env — если утечёт, полный доступ к БД. Хранить в Vercel secrets, не логировать.

### Бэкапы

- Supabase Free: ежедневные бэкапы, 1 день retention
- **Действие:** Перейти на Pro plan ($25/мес) для 7-дневных PITR бэкапов при первых 3-5 платящих клиентах
- Ручной бэкап: `pg_dump` через Supabase CLI раз в неделю в git-ignored папку

### Производительность при масштабировании (единый API ключ)

**Текущая архитектура:** Один `ANTHROPIC_API_KEY` для всех бизнесов.

**Проблемы при росте:**
1. **Rate limits Anthropic:** Tier 1 = 50K tokens/min. При 100 активных бизнесах, каждый генерирует 500 tok/min → упрётся в лимит
2. **Стоимость непредсказуема:** Один активный бот может съесть весь бюджет
3. **Нет изоляции отказов:** Один бизнес со спамом блокирует других

**Решения по уровням:**
- **MVP (до 20 бизнесов):** Текущая архитектура. Жёсткий `messages_limit` в подписке. Hard cap $30/мес в Anthropic Console.
- **Рост (20-100 бизнесов):** Добавить очередь (BullMQ или Supabase pg_queue). AI запросы обрабатываются последовательно с throttling.
- **Масштаб (100+ бизнесов):** Рассмотреть self-hosted открытые модели (Mistral, Llama) для базовых ответов. Claude только для сложных случаев.

**In-memory rate limiter (Vercel):**
Vercel — serverless, каждый invocation независим. Rate limiter в `Map` работает только в рамках одного cold start.
- **Реальная защита:** Квота `messages_limit` в БД (там всё честно)
- **Для строгого rate limit:** Нужен Redis (Upstash ~$0 на старте)
- **Сейчас:** Принять риск, мониторить через Vercel logs

## Юридические вопросы (152-ФЗ, оплата, ПД)

### Что делать сейчас (до первых пользователей)

1. **Политика конфиденциальности** — разместить на сайте. Минимальный шаблон:
   - Что собираем: email регистрации владельца, Telegram данные клиентов его бота
   - Как используем: для работы сервиса
   - Где храним: серверы ЕС (Supabase Frankfurt)
   - Как удалить: email на удаление

2. **Согласие на обработку** — чекбокс "Я согласен с политикой" на /register

3. **Трансграничная передача данных:**
   Supabase Frankfurt = хранение за пределами РФ.
   По 152-ФЗ обязательна запись в базе Роскомнадзора и первичное хранение в РФ.
   **Практика:** 90% российских стартапов игнорируют это до масштаба. Риск = штраф до 500K руб при проверке.
   **Решение при росте:** Переехать на Yandex Cloud Managed PostgreSQL или VK Cloud.

4. **Самозанятый + YooKassa:**
   - Чек выставляется через YooKassa автоматически при оплате — ОК
   - Лимит 2.4M руб/год. При 135 клиентах × 1490₽ × 12 мес = 2.4M — порог.
   - Заранее открыть ИП УСН 6% к этому моменту

5. **Договор-оферта** — публичная оферта на сайте о предоставлении SaaS услуги

### Что отложить

- Полное соответствие 152-ФЗ (локализация) — при 50+ платящих клиентах
- DPA (Data Processing Agreement) с бизнесами — при корпоративных клиентах
- Уведомление Роскомнадзора — перед первой PR-кампанией

## UX/UI — что улучшить

### Быстрые wins (1-2 дня)

1. **Оптимистичные обновления в формах**
   После сохранения не ждать SSR revalidation — сразу обновлять UI.
   Использовать `useOptimistic()` или просто не ждать `router.refresh()`.

2. **Toast-уведомления вместо inline сообщений**
   Сейчас: "Сохранено" появляется рядом с кнопкой.
   Лучше: toast в углу экрана на 3 секунды (sonner lib).

3. **Confirm modal вместо `window.confirm()`**
   Сейчас: нативный диалог браузера при удалении.
   Лучше: кастомный modal "Вы уверены? Это действие нельзя отменить."

4. **Дата записей по timezone бизнеса**
   Сейчас: UTC. Нужно читать `business.settings.timezone`.

5. **Пустые состояния** с CTA
   Если нет сервисов — показать "Добавьте первую услугу" с кнопкой.
